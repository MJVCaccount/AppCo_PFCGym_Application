## XSS

React escapes every value rendered in JSX, and `grep -rn "dangerouslySetInnerHTML\|innerHTML\|eval(" src` returns nothing. HTML is built by hand in one place, the email templates, where every interpolated value goes through `escapeHtml` (row 13). The CSP (row 5) is the second layer: a script that is injected without this request's nonce is refused, inline event handlers and `javascript:` URLs are blocked for the same reason, and `form-action` and `connect-src` are limited to the site. Hostile text (`<script>alert(1)</script>`, `<img onerror>`) is submitted to every text field in `tests/hostile-input.test.ts` and `tests/flows.test.ts` and stored as plain text. `'strict-dynamic'` trusts script elements that a script which is already trusted creates; that is how the policy is meant to work. A browser check that creates script elements through DevTools is exempt from the policy, so those results (an inline script and a `data:` script created that way did run, and so did `eval()`) say nothing about page code. In a real browser the injection routes that matter were blocked: inline event handlers (`onerror`, `onclick`), `javascript:` URLs, scripts set through `innerHTML`, `document.write`, and script files from other hosts (and `fetch` to another host was blocked by `connect-src`). Nothing more than that was tested: a vulnerability that builds script elements from user input would not be stopped by this policy, and none was looked for beyond the review of `dangerouslySetInnerHTML`, `innerHTML` and `eval(` above. `style-src` includes `'unsafe-inline'` (`src/lib/csp.ts`), so injected CSS is not blocked.

## POPIA and fighter documents

* **What is stored.** A fighter may upload Medical, Licence or Other documents (PDF, JPEG or PNG, at most 4 MB each, at most 10 per fighter). The file goes to the private Blob store under `fighter-docs/<fighterId>/<uuid>.<ext>`. The database holds a `FighterDocument` row: type, a sanitised original file name, the pathname in `fileUrl`, review status, review note and dates (`prisma/schema.prisma:230`). Medical documents are special personal information under POPIA (`src/lib/services/documentService.ts` header comment states this intent). Whether a legal basis, consent text or retention period exists: **not verified** (nothing in the repository defines one).
* **Who can read it.** The owning fighter and any admin, only through `GET /api/documents/:id`, which streams it as a download. Other members, coaches, other fighters and guests get 404 or 401. There is no public URL and the blob URL is never sent to a browser. Admins can see the file name, type and status in `/admin/documents`. Access by an admin is not audited (row 14).
* **How it is deleted.** The owner can delete a document while it is Pending or Rejected: the row is deleted in a transaction and then the blob is deleted (best effort; a failed blob delete is logged with the pathname and the row stays deleted) (`deleteOwnDocument`, `removeBlob`). An Approved document cannot be deleted by the owner (409). A fighter with any document cannot be demoted (409). Deleting an account cascades the rows (`onDelete: Cascade` on `Fighter` → `FighterDocument`) but there is no code that deletes the blobs for a removed account, and the app has no feature for deleting an account at all: both **not verified** beyond what is stated here. A failed upload that stored a blob but could not save the row deletes the blob (`documentService.ts`).
* **Logging.** The log records the pathname on a failed delete; it records the recipient's domain, not the address, when an email fails (`src/lib/email/send.ts`). Log retention is a Vercel setting: **not verified**.
